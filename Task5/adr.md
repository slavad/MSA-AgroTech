#### Критерии сравнения

| Критерий | Схема на тенанта | БД на тенанта | Виртуальный инстанс на тенанта | Физический инстанс на тенанта |
| --- | --- | --- | --- | --- |
| Диаграмма | [schema-per-tenant](./C2_isolation_schema-per-tenant.puml) | [db-per-tenant](./C2_isolation_db-per-tenant.puml) | [virtual-instance-per-tenant](./C2_isolation_virtual-instance-per-tenant.puml) | [physical-instance-per-tenant](./C2_isolation_physical-instance-per-tenant.puml) |
| Траты на тенанта | Низкая | Средняя | Высокая | Самая высокая |
| Время онбординга | Минуты (создаем схему, бутстрапим ее) | Минуты (создаем базу, бутстрапим ее) | Десятки минут (создаем VM, базу, бутстрапим ее) | Часы, дни (нужен отдельный физический сервер) |
| Горизонтальное масштабирование | Ограничено размером одного кластера | БД могут быть распределены по узлам кластера | Просто, но расходы на облако растут пропорционально числу тенантов | Просто, но рост операционных расходов большой (на железо и обслуживание) |
| Изоляция данных тенантов | Низкая | Средняя | Высокая | Высокая |
| Конкуренция между тенантами за общие ресурсы системы | Высокая | Средняя | Низкая (остаточный риск на уровне гипервизора) | Отсутствует |

#### Выбор

Можно использовать все 4 варианта, но на разных тарифных планах для клиентов.
В зависимости от размера клиента выбираем один из 4 вариантов разделения данных и соотв. тарифный план.



### Задача 2. Биллинг и монетизация

#### Сервисы тарификации и биллинга

Новые сервисы: `Subscription & Plan Service`, `Usage Metering Service` (переиспользует конвейер `Metrics Export Service` из MVP, помечая события tenant_id), `Billing & Invoicing Service`, `Payment Gateway Adapter`.



#### Интеграция с российскими платежными системами



#### Вариант А

Оплату осуществляем с использованием какого-либо агрегатора или нескольких (ЮKassa, Yandex Pay и т.д.).

Преимущества

1. Ограниченное кол-во API, вместо интеграции с каждым банком
2. Резервирование (отказоустойчивость), если один из платежных шлюзов не работает

Проблема: агрегатор берет свою комиссию.

#### Вариант B

Переводом на счет с ручной обработкой. Имеет смысл с большими клиентами, где время на ручную обработку оправдано.

Преимущества:

- Нет комиссии агрегатора

Недостатки

- Ручная обработка



Диаграмма: [`C2_saas_final.puml`](./C2_saas_final.puml) -- `Billing & Invoicing Service`, `Payment Gateway Adapter`, `Subscription & Plan Service`, `Usage Metering Service` и их связь с "Платежные системы РФ".

### Задача 3. Интеграции с клиентами

Диаграмма: [`C2_saas_final.puml`](./C2_saas_final.puml) -- контейнер `Public Client API`.

##### Публичный API Scope

1. Чтение метрик, инцидентов, отчетов по фермам
2. Подписка на вебхуки (об инцидентах)
3. Управление конфигурацией своих агентов и ферм
4. Управление юзерами и ролями
5. Доступ к данными биллинга своего аккаунта

##### Dev-портал

1. документация по API
2. Сендбокс-тенант для экспериментов с API
3. Управление своими ключами доступа

#### Описание решения

Клиенту предлагается на выбор несколько тарифных планов, и в зависимости от плана мы используем различные варианты изоляции данных. Для обработки платежей используем несколько российских платежных систем (можно добавлять по мере необходимости). Использовать ручную обработку или интеграцию с банками нет смысла -- у нас нет таких больших клиентов, чтобы была какая-либо выгода от отсутствия комиссии.

Для онбординга разработчиков используем портал разработчика, где можно посмотреть документацию, протестировать работу API в сендбоксе и управлять ключами доступа.

2. Что если клиент захочет провести миграцию на более дорого тарифный план. Миграция займет много времени, и она должна быть бесшовной
